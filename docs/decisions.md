# Engineering Decisions — Edge Case Checklist

This document works through every item in the capstone feature list PDF (`Digital Banking Backend + Ops Automation — Capstone feature list`, 7 domains, 32 items) and records the actual, justified decision for each: what was built, what was deliberately scoped out, and why. Cross-references point at the real schema (`supabase/migrations/`), RPCs, and n8n workflows (`n8n/workflows/`) rather than restating them.

Status legend: **✅ Built** — implemented and live · **⚠️ Partial** — a simplified version is built · **⛔ Scoped out** — deliberately not built for this submission, with reasoning.

> **Update (2026-09-15):** Several items marked "Scoped out" below were subsequently implemented in a second engineering pass — the user asked for them explicitly (real self-service account opening, joint account invitations, minor/guardian accounts, majority-vote governance, either-or vs. both-signature authority, PKR as the system currency, and a public RAG chatbot). Each affected row is annotated in place; full detail on the new work is in **[Session 2 Addendum](#session-2-addendum-account-opening-joint-invitations-pkr-governance-public-rag)** at the end of this document. Treat the addendum as authoritative where it conflicts with the original row text below.

## 1. Account Types & Ownership

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 1 | Single-holder account creation and management | ✅ Built | `accounts` + `account_holders` with `role = 'primary'`. This is the baseline path exercised by every test scenario. |
| 2 | Joint account creation with 2+ holders | ✅ Built | Multiple `account_holders` rows per `account_id`, `role = 'joint'`. Seed data includes `TEST-JOINT-001` with Alice + Charlie. |
| 3 | Either-or vs. both-signatures authority model | ✅ Built (Session 9) | `account_holders` has no authority-model column. **Decision: default to either-or (any holder can act unilaterally) for all joint actions except closure**, which is the one place the PDF explicitly calls for stronger protection (see #4). Both-signature authority for ordinary transfers would need a pending-approval table mirroring `joint_account_actions` for every transaction type, which is real scope for a v2, not a schema flag.  **Superseded in Session 9:** `accounts.authority_model` (`either_or` / `all_signatures`) is now set from the customer's own words when they invite someone to a joint account, and `initiate_transfer()` enforces it — an `all_signatures` account parks the transfer as a `joint_account_actions` row and emails every other holder a `JNT-XXXXXXXX` code they reply APPROVE or REJECT to. The "pending-approval table mirroring joint_account_actions" this row said would be needed already existed; what was missing was the enforcement call and the email round-trip. |
| 4 | Mutual consent requirement for removing a joint holder | ✅ Built (Session 11) | Only account *closure* has a consent workflow (`joint_account_actions` / `joint_account_consents`, action_type constrained to `'close_account'`). Removing a single holder while keeping the account open is a different state machine (who inherits their share of holds/standing orders?) and was not built. Decision: unsupported in this MVP; the only supported multi-holder action is full closure.  **Built in Session 11.** `remove_holder` is now a joint action type. Mutual consent means EVERY holder signs, **including the person being removed** — you cannot be ejected from an account you are liable for without agreeing, and you cannot walk away unilaterally either. Refused outright while the account carries an outstanding loan or an active hold (you cannot shrink the set of people answerable for a debt), when it would leave the account with zero holders (close it instead), or when it would strip a guardian off an account a minor still holds. Verified live: Alice alone could not remove Bob; it executed only once Bob also agreed. |
| 5 | Majority-vote vs. either-or authority for 3+ holder joint accounts | ✅ Built (Session 9) | `record_joint_consent()` requires **unanimous** consent (checks that every holder has responded and every response is `consent = true`) before `close_account()` fires — not majority-vote, and not either-or. Decision: unanimous consent is the conservative default for the one high-stakes joint action we support (closure). Majority-vote was rejected as a default because it lets 2 of 3 holders close an account and force a payout split the third holder never agreed to — too risky to ship without a dispute-resolution path behind it.  **Superseded in Session 9:** `accounts.closure_authority` (`unanimous` / `majority`) is respected by `finalize_joint_action_if_complete()`, which requires `floor(n/2)+1` consents for a `close_account` action on a `majority` account with 3+ holders and unanimity otherwise. `unanimous` remains the default for the reason given above. |
| 6 | Minor/guardian account with guardian-acts, minor-views-only permissions | ✅ Built (Session 9) | No age/guardian columns on `profiles` or a permissions layer on `account_holders`. This needs a `role IN ('guardian','minor')` distinction plus a permissions matrix (minor: SELECT only; guardian: full CRUD) enforced in RLS *and* in every n8n intent handler. Real effort, not a flag. Decision: out of scope; `account_holders.role` stays `primary | joint | beneficiary`.  **Superseded in Session 9:** the permissions layer described here exists (`account_holders.holder_type` = adult/minor/guardian, `guardian_of_profile_id`, `is_holder_transfer_authorized()`), and Session 9 connected it to a real customer path — account opening asks for a date of birth, an under-18 applicant cannot proceed alone, the named guardian must reply APPROVE to a `MIN-XXXXXXXX` code, and the resulting account has the minor as `primary`/`minor` and the guardian as `joint`/`guardian`. `initiate_transfer()` refuses a transfer initiated by a minor holder; the guardian can transfer normally. Verified live end to end. |
| 7 | Age-based trigger to convert minor account to full access | ✅ Built (Session 9) | Depends on #6 existing first (no `date_of_birth` on `profiles` either). Would be a nightly scheduled RPC similar to `run_reconciliation()`. Not built.  **Superseded in Session 9:** `promote_minors_to_adult()` existed and WF-06 already ran it nightly, but no profile had a `date_of_birth` for it to act on, so it could never fire. Account opening now captures and stores the date of birth, which makes the nightly promotion real. |
| 8 | Adding a new holder to an account with existing debt/holds | ✅ Built (Session 11) | There's no "add holder" RPC at all today — holders are only ever seeded or created at account-opening time. `place_account_hold` and negative-balance tracking exist, but nothing stops (or explicitly permits) attaching a new `account_holders` row to an account that already has an active hold. Decision: until an explicit "add holder" flow is built, this can only happen via direct DB access, which is an ops action, not a customer-facing one — so it's not a live edge case yet.  **Partly superseded in Session 9:** `add_account_holder()` exists and takes `p_acknowledge_active_holds`, refusing to attach a holder to an account with active holds unless that flag is passed, and `joint_account_actions.action_type` accepts `'add_holder'` so it can be gated behind co-holder consent. What is still missing is a customer-facing email intent that starts the flow — today it can only be invoked by RPC.  **Completed in Session 11.** `request_holder_addition()` now surfaces every encumbrance — active holds, outstanding loan balance, unpaid debt — in the approval request, so nobody inherits a liability silently. And the decision the brief is really probing: **the person being added must accept too**, not just the existing holders. That needed its own mechanism (`accept_holder_addition()`), because `record_joint_consent()` verifies the consenter is already a holder, which the incoming person by definition is not. Verified live against an account carrying a Rs 315,000 loan: both existing holders approved, the action stayed pending with `awaiting_invitee_acceptance`, and only completed when the invitee accepted. |
| 9 | Joint account closure rule when holders disagree | ✅ Built | Unanimous-consent model means disagreement = the request simply never reaches 100% approval. `joint_account_actions.expires_at` (7 days, see migration `001`) auto-times out a stalled request rather than leaving it open forever. No forced closure over a dissenting holder — matches the conservative posture in #5. |

## 2. Transactions & Transfers

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 10 | Idempotency key handling to prevent duplicate transfer submissions | ✅ Built | `idempotency_keys` table, atomic `INSERT ... ON CONFLICT DO NOTHING` inside `execute_transfer()`. A retried key with a `completed` status returns the stored result instead of re-executing. WF-00 derives the key deterministically from the Gmail `messageId` (`gmail_<messageId>`), so re-sending the same email is naturally idempotent. |
| 11 | Postgres transaction isolation to prevent concurrent-withdrawal overdrafts | ✅ Built | `execute_transfer()` takes `SELECT ... FOR UPDATE` row locks on both accounts (in a fixed account-id order to avoid deadlocks) before checking `get_available_balance()`, inside one Postgres transaction. `tests/test_concurrency.sql` exercises this directly. |
| 12 | Rollback logic for partial transfer failure (debit succeeds, credit fails) | ✅ Built | The whole transfer — idempotency check, lock, fraud check, hold check, balance check, both ledger inserts, both balance updates, audit — runs inside the single `execute_transfer()` PL/pgSQL function body. Any exception anywhere rolls back the entire function atomically; there is no code path where a debit can commit without its matching credit. |
| 13 | Notification flow when a transfer is rolled back | ✅ Built | WF-01's `Check RPC Result` branch on `success = false` and emails an ops alert (`Email Ops - Transfer Failed Alert`) with the error and idempotency key; WF-00 separately emails the customer a plain-language failure notice with no funds-moved confirmation. |
| 14 | Reversal/chargeback handling after funds already spent (negative balance/debt tracking) | ✅ Built (Session 11) | `accounts.balance` has `CHECK (balance >= 0)` — the schema actively **forbids** negative balances. A real chargeback-after-spend flow needs a separate `debt_ledger`/`overdraft` concept that intentionally violates the "balance is truth, never negative" invariant everywhere else in the system. Decision: rather than special-case one table to allow negative balances (weakening the ledger's core guarantee), this is left as a documented gap — a dispute that nets to a loss becomes an ops-managed write-off outside the automated ledger, not an automated negative-balance entry.  **Built in Session 11 — this row's original reasoning was sound but the conclusion was wrong.** The objection was that allowing a negative balance would weaken the ledger's core guarantee. True — so the shortfall is not modelled as a negative balance. `reverse_transaction()` claws back whatever the recipient still has via the same double-entry primitive as any transfer, and records the unrecoverable remainder in `account_debts` as an explicit **receivable**, which is how a real bank models it. `CHECK (balance >= 0)` is untouched and no balance ever goes negative. `sweep_outstanding_debts()` collects the debt nightly from whatever the account receives later. Verified live: Rs 2,000 sent, Rs 1,500 spent, reversal recovered Rs 500 and booked Rs 1,500 of debt, then collected it across two later deposits until settled — with reconciliation clean at every step. Reversal is reachable **only** through a human decision (an upheld dispute or an ops-approved reversal), per #27. |

## 3. Standing Orders / Scheduled Payments (n8n)

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 15 | Weekend/holiday scheduling rule (process early, late, or pending state) | ✅ Built (Session 11) | WF-02 runs hourly and fires any order where `next_execution_at <= NOW()` — no calendar/holiday awareness. Decision: for a hackathon-scope banking backend, real-time ACH-style settlement isn't gated by banking-holiday calendars the way real interbank rails are (this system settles instantly, internally, via the ledger) — so the holiday-deferral problem this rule solves for real banks doesn't apply here. Documented as a known simplification rather than silently ignored.  **Built in Session 11.** The original reasoning — that instant internal settlement makes interbank holiday deferral inapplicable — still holds, which is why `allow_weekend` remains a legitimate configurable choice rather than a bug. But the `weekend_holiday_rule` column existed with three legal values and only weekends were ever honoured; there was no holiday calendar at all. Added `bank_holidays` (Pakistan national holidays, with lunar Eid dates flagged `is_estimated` so they are corrected each year rather than trusted), plus `is_business_day()` and `adjust_for_business_day()` supporting all three rules. Verified: a payment due Friday 14 August 2026 (Independence Day) rolls to Monday the 17th under `next_business_day`, back to Thursday the 13th under `process_early`, and stays put under `allow_weekend`. |
| 16 | Insufficient-funds retry policy (same day, next day, max retry count) | ✅ Built | `execute_standing_order()` increments `standing_orders.retry_count` on failure and reschedules; WF-02's `Permanent Failure?` node checks `retry_count >= 3` (max 3 retries) OR an explicit `'failed'` status from the RPC, and disables the order permanently past that point. |
| 17 | Customer notification when a standing order permanently fails | ✅ Built (revised Session 11) | WF-02 → `Format Permanent Failure Alert` → `Email Ops Team - Standing Order Failed`. Note: this currently emails **ops** (a dedicated ops inbox, not the customer's own address), not the customer directly — decision: a permanently-failed recurring payment is treated as an ops-triage event first (does the customer need outreach, is this a systemic issue, etc.) rather than an unsupervised customer email, consistent with the "always requires human sign-off" boundary in domain 6. |
| 18 | Race-condition handling when a standing order is edited/deleted mid-execution | ✅ Built | `standing_orders.execution_locked_at` is a stale-lock timestamp column: `execute_standing_order()` locks the row before executing, so a concurrent edit/delete blocks on the same row lock rather than racing the in-flight execution. |

## 4. Interest, Statements & Reconciliation (Python)

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 19 | Nightly reconciliation job comparing ledger sum vs. reported balance | ✅ Built (completed Session 11) | WF-06 (midnight UTC cron) → `run_reconciliation()` RPC checks (a) system-wide `SUM(debits) = SUM(credits)` and (b) every account's cached `balance` against its ledger-entry sum. Results land in `reconciliation_runs`; a mismatch triggers `Email Ops Team - Reconciliation Mismatch`. Note: the PDF frames this as a Python job, but it's implemented as a Postgres RPC triggered by n8n's scheduler — the actual arithmetic is simple aggregate SQL, and running it inside Postgres means it reads the ledger under the same transactional guarantees that wrote it, with no network round-trip that could see a half-committed state. Interest calculation itself (the other half of this domain's Python framing) was not built — no interest-bearing account type or rate schedule exists yet.  **Completed in Session 11.** Reconciliation was built; the other two thirds of this domain were not. Interest: `interest_rates` (savings 5% p.a., checking and business 0%) and `accrue_monthly_interest()`, paid from `TREASURY-MAIN` through the same double-entry primitive as every other movement so interest income appears in the ledger and in reconciliation. Idempotent via a unique constraint on `(account_id, period_start)`, so the nightly job cannot pay a month twice — verified by running it twice and seeing the second run skip. Statements: `generate_account_statement()` derives the opening balance from the ledger itself rather than any cached figure, so a statement is reconstructable from the ledger alone. |

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 20 | RAG-based auto-draft response to customer support queries | ✅ Built | WF-04: LangChain agent (Groq `openai/gpt-oss-safeguard-20b`) with a Pinecone-retrieval tool (`banking-policy-index`, namespace `banking_policy`, Gemini `gemini-embedding-001` embeddings — `text-embedding-004` was the model at the time of this original entry but has since been retired by Google), structured JSON output (`draft`, `grounded`, `confidence`, `citations`, `needs_human`). *At the time this row was first written, the Pinecone index didn't exist yet and retrieval always came back empty — that's long since resolved: the index is created, seeded with 13 documents (`docs/policies.md`), and verified live and grounded. | 21 | Hallucination guardrails so RAG never invents non-existent policy | ✅ Built | The agent's system prompt hard-bans inventing policy and requires citations; `Grounded & Confident? (>= 0.7)` gates on both `grounded = true` AND `confidence >= 0.7`. Below that bar, `Insufficient Policy Fallback Draft` overrides the model's own text entirely with a fixed "requires specialist review" message — the LLM's raw draft is never sent to a customer when it isn't grounded, regardless of how confident-sounding it is. |
| 22 | Immediate fraud-flag hold trigger and false-positive handling for legitimate large purchases | ✅ Built | WF-03: risk score ≥ 75 → `place_account_hold()` full freeze, `fraud_investigation` type, ops alert. False-positive handling is `release_account_hold()` — but this is intentionally **not** an automated appeal path (customer can't self-clear a fraud hold); it requires a human operator to invoke the release RPC. See domain 6 (#26). |
| 23 | Dispute resolution rule for joint accounts (unilateral vs. both-holder input) | ✅ Built (Session 11) | WF-00's `DISPUTE` intent only sends an acknowledgement email and relies on a human specialist for the actual investigation (see `Send Dispute Acknowledgement Email`); there's no automated joint-account-specific dispute rule. Decision: disputes are inherently investigative and already routed to a human by design (domain 6), so an automation-level unilateral-vs-both-holder rule would be deciding something a human is about to decide anyway — redundant to build.  **Built in Session 11 — the original reasoning conflated "a human decides" with "no rule is needed".** A human still decides every dispute; what was missing was the rule governing *who gets a say*. Now explicit and enforced: **raising is unilateral** (requiring co-holder sign-off to report suspected fraud would gate the fastest way to stop money leaving behind someone who may be asleep, unreachable, or the problem); **input is collected from every other holder**, who are emailed and reply AGREE or DISAGREE with a comment; **resolution is never automatic and never unilateral**, and the operator is shown whether the co-holders agreed. Verified live on a 3-holder account: Bob raised it, Alice agreed, Charlie said he had authorised it, a non-holder was refused, and ops decided with all three positions in front of them. |
| 24 | Human approval gate before any RAG-drafted response is sent via Gmail | ✅ Built (revised Session 5) | Originally every RAG answer, regardless of confidence, sat behind WF-05 — the customer only ever got a "we're reviewing it" receipt. That made human review a bottleneck on every policy question, which isn't practical for a public chatbot. Now: a grounded, confident (≥ 0.7) answer is sent to the customer directly by WF-04, no human step. Only ungrounded, low-confidence, or agent-error cases are queued in `support_case_drafts` (`human_review_state = 'pending'`) and require an explicit `POST /webhook/approve-draft` (`action: approve|edit|reject`) via WF-05 before anything reaches the customer. The gate still exists and is still the only path for a case in that state to be answered — it's just no longer applied to every case indiscriminately. See `decisions.md` Session 5 and `docs/policies.md`. |
| 25 | Safeguards against Pinecone surfacing a similar-but-wrong past case for drafting | ✅ Built (Session 11) | The confidence/grounded threshold (#21) is the safeguard that exists today — a wrong-but-similar match that the LLM can't stitch into a confident, citation-backed answer gets routed to a human instead of sent. What's **not** built: explicit metadata filtering (e.g. product line, jurisdiction, account type) on the Pinecone query to stop a similar-sounding-but-wrong-category document from being retrieved in the first place. Decision: out of scope until the index itself is populated with real policy documents that have that metadata to filter on.  **Built in Session 11.** Two safeguards now, and the first is structural: **past support cases are never indexed at all.** Only policy documents enter the vector store, and fraud typologies live in a separate `fraud_patterns` namespace, so the specific failure this row describes — a similar-but-wrong *past case* surfacing — cannot occur by construction. Second, a citation guardrail catches the related failure the confidence threshold cannot: an answer claiming `grounded: true` with **zero citations** is forced to human review whatever confidence it reports, because a model reciting plausible banking knowledge from training rather than from our documents has nothing to cite. Retrieval is also bounded to `topK` 4 so a weak match cannot pad the context. |

## Known live issues at time of this audit (2026-09-14)

These are infrastructure/config problems found and partially fixed during this review — see `README.md` "Known Dependencies" for current status:

1. **n8n → Railway Python service URL was missing its `https://` scheme** in the `PYTHON_SERVICE_URL` instance variable, causing every fraud check to error and fail safe into a hold. Fixed in WF-00 and WF-03 by normalizing the URL in the HTTP Request node itself instead of trusting the variable's format.
2. **`place_account_hold` RPC response broke n8n's JSON auto-detect** (it `RETURNS UUID`, a bare scalar, unlike every other financial RPC which returns `JSONB`) — fixed by forcing `responseFormat: text` on that HTTP Request node.
3. ~~The Railway-deployed Python service itself is rejecting requests with "Supabase credentials missing from environment configuration"~~ — **resolved by the user** on Railway's dashboard (2026-09-15).
4. ~~The Pinecone index `banking-policy-index` does not exist~~ — **resolved by the user**, who created the index. See the [Session 2 Addendum](#session-2-addendum-account-opening-joint-invitations-pkr-governance-public-rag) for a second, more subtle issue found immediately after (Google retired the embedding model this project was built around) and its fix/remaining action.
5. Two of the three published n8n workflow drafts (WF-00, WF-01, WF-04) had newer, safer logic sitting unpublished in the editor — the *live* versions had hardcoded fallback account IDs and a hardcoded fallback "approved" fraud-assessment ID that would activate on malformed input instead of rejecting the request. Republished all three to their improved drafts as part of this review.

## Session 2 Addendum: account opening, joint invitations, PKR, governance, public RAG

Everything in this section was added after the original audit above, in direct response to explicit follow-up requests: finish self-service account opening, add joint account invitations with a 5-minute accept/decline window, switch the whole system to PKR, and make the RAG assistant a public chatbot rather than customers-only.

### Schema (`supabase/migrations/005_pkr_currency_joint_invitations_public_rag.sql`)

- **PKR as the system currency**: `accounts`, `standing_orders`, and `transactions` all default to `'PKR'`; existing `'USD'` rows were updated in place. The minor-unit design is unchanged — paisa (1 PKR = 100 paisa) occupy the same `BIGINT` column that used to hold cents.
- **`joint_account_invitations`** (new table): `inviter_profile_id`, `invitee_email`, `status` (`pending`/`accepted`/`rejected`/`expired`), `expires_at` defaulting to `NOW() + 5 minutes`, `account_id` (set on acceptance). RLS enabled, deny-all for `anon`/`authenticated` (service_role only, same pattern as migration 003).
- **`support_cases.profile_id` is now nullable**, with a new `customer_email` and `inquirer_type` (`customer`/`public`) — a `CHECK` constraint requires at least one identity field. This is what makes the RAG assistant usable by anyone, not just registered customers.

### New RPCs

- **`open_account_for_profile(profile_id, account_type, currency, holder_type, guardian_profile_id)`** — creates an account and its first `account_holders` row; if `holder_type='minor'`, also inserts the named guardian with `holder_type='guardian'` and `guardian_of_profile_id` pointing at the minor. Generates account numbers as `ACC-XXXXXXXXXX`.
- **`add_account_holder(account_id, new_profile_id, role, requested_by_profile_id, acknowledge_active_holds)`** — implements edge case #8 (adding a holder to an account with active holds): refuses with `requires_acknowledgment: true` unless the caller explicitly passes acknowledgment.
- **`finalize_joint_action_if_complete`** — generalizes the old closure-only consent-counting logic to also finalize `transfer_approval` and `add_holder` joint actions. Implements majority-vote governance (edge case #5): unanimous by default, strict majority only for `closure_authority='majority'` accounts with 3+ holders.
- **`request_transfer_approval` / `initiate_transfer`** — implements either-or vs. both-signature authority (edge case #3): `initiate_transfer` is the new n8n-facing entry point (same signature as `execute_transfer`) that checks `accounts.authority_model` and routes to an immediate transfer (`either_or`, the default) or a pending multi-holder approval (`all_signatures`) requiring every holder's consent before money moves. **Verified live**: a real test transfer from a 2-holder `all_signatures` account correctly blocked until the second holder consented, then executed atomically — no partial state, no duplicate execution on a repeated consent call.
- **`create_joint_account_invitation` / `respond_to_joint_invitation` / `expire_stale_joint_invitations`** — the joint invitation lifecycle. `respond_to_joint_invitation` is idempotent (a duplicate accept/reject returns the already-settled state, verified live, no duplicate account created) and returns `needs_profile_creation: true` when the invitee isn't yet a customer, so n8n can provision them and retry with the same invitation untouched.
- **`promote_minors_to_adult`** and **`is_holder_transfer_authorized`** — implement the age-based trigger (edge case #7) and minor/guardian view-only enforcement (edge case #6). `profiles.date_of_birth` and `account_holders.holder_type` (`adult`/`minor`/`guardian`) were added for this.
- All new functions follow the existing security model exactly: `SECURITY DEFINER`, owned by `banking_functions`, `REVOKE ... FROM PUBLIC` + `GRANT ... TO service_role` only. This pass also closed a latent gap from migration 001: `execute_transfer`, `execute_standing_order`, `place_account_hold`, `release_account_hold`, `request_joint_closure`, `record_joint_consent`, and `run_reconciliation` were all implicitly executable by `PUBLIC` (Postgres's default) and are now explicitly locked down too.

### How account opening actually works now

- **Single account, brand-new sender**: WF-00 detects "open an account" from an unregistered sender, creates a real (but not KYC-verified) customer record via Supabase's Auth Admin API — a deliberate, explicit decision for this fake-bank hackathon context (no real identity verification, matching the PDF's "not required to implement real KYC" framing) — then calls `open_account_for_profile` and replies with the real account number in PKR. **This creates a genuine login-capable Supabase Auth user from unauthenticated email content**, which is a real security-relevant trade-off; it was deliberately scoped to this project's fake-bank context and would not be appropriate for a real bank.
- **Single account, existing customer**: same RPC, using their already-verified `profile_id` — no new Auth user needed.
- **Joint account**: the inviter (existing customer or, in principle, a brand-new sender) names an invitee's email; a `joint_account_invitations` row is created with a real 5-minute clock, and both parties are emailed. The invitee's *reply* (to the same bank inbox WF-00 already polls) is matched against pending invitations addressed to their email and parsed for accept/decline language — the invitee's own identity is *never* trusted from anything written inside the email body, only from the verified Gmail sender address, consistent with the project's existing "the Gmail sender is the identity" rule. Accepting when the invitee isn't yet a customer triggers the same Auth Admin API provisioning as single-account opening, then retries the same invitation.
- **Expiry**: WF-08 (new) sweeps every minute for invitations past their 5-minute window, marks them expired, and emails the inviter that the invitee didn't respond in time.

### Public RAG chatbot + returning-visitor memory

WF-04 no longer requires `profile_id` — anyone's `customer_email` is enough to ask a policy question. A lookup against `support_cases.customer_email` within the last 10 minutes flags returning visitors, and the LLM is told to acknowledge that in tone (never told to relax its grounding rules). **A real bug was found and fixed during this pass**: with an empty Pinecone index, the LangChain agent retried its search tool until it hit the 10-iteration cap and crashed the whole workflow instead of returning its own "not grounded" fallback — the exact failure mode the PDF's "good error handling" requirement is about. Fixed two ways: the prompt now hard-caps search attempts at 2, and the agent node has a dedicated error-output branch that still produces a clean "couldn't find that in our policy documents, a specialist will follow up" message instead of ever surfacing a raw crash to a customer.

Seeding the Pinecone index (`n8n` workflow **WF-09**, new, one-time utility) surfaced that **Google has retired the embedding models this project was built around** (`text-embedding-004` and `embedding-001` both now return `404 Not Found`). ### Session 3: three real bugs the user caught by inspection, not by testing

The user reviewed the WF-00 design (not just the output) and correctly flagged three problems before they were ever exercised live:

1. **A genuinely silent drop.** `New Sender Route`'s Policy output (index 1) was never wired to anything — an automated audit of every IF/Switch node's connections confirmed this was the *only* unwired branch in the whole 57-node workflow (every other branch, including the ones that intentionally do nothing like "don't bother emailing the inviter when there's nothing new to say", was accounted for). A brand-new person emailing "what are your ATM fees?" got no reply at all. Fixed by wiring it into WF-04's public RAG path with its own receipt email.

A stale or reused subject line (e.g. an old "Fraud" thread reused to ask a balance question, or a forwarded email) could out-rank what the customer actually wrote in the body. Fixed: the body is now checked first in isolation; the subject is only consulted as a fallback when the body itself yields no match at all (e.g. a one-line email with everything in the subject).
3. **False-positive collision risk in invitation-response detection.** The accept/decline detector originally matched on bare words like "yes" or "accept" anywhere in the body. Someone who happened to have a pending joint invitation *and* separately emailed something like "yes please transfer 5000 to bob" would have been misrouted into the invitation-response flow instead of the transfer flow. Fixed: now requires either explicit phrasing ("I accept the invitation") or a short (≤8 word) reply that contains no other strong banking keyword (transfer/balance/policy/open-account/etc.) — a real invitation reply is short and single-purpose, so this cheaply disambiguates without needing an LLM call.

All three were fixed and re-validated (automated connection-completeness audit re-run clean; the empty-body fallback and the public-policy routing both re-tested live). The `Check Pending Joint Invitation` step itself was **not** removed despite adding one extra query per email — it's what makes accept/decline replies work for *any* sender, registered or not, and a single indexed lookup against a small table is not a practical performance concern for an inbox polled once a minute. The actual complaint (a pending invitation silently swallowing an unrelated request) is what got fixed, not the check's existence.

### Session 4: WF-08 was quietly burning the n8n execution quota

The user caught a real cost problem: WF-08 ran on a **Schedule Trigger** every 1 minute — and unlike Gmail's *polling* trigger (which only creates an execution when there's actually new mail), a Schedule Trigger fires unconditionally on every tick whether or not there's any invitation to expire. That's ~1,440 wasted executions/day against an n8n Cloud free-tier quota of 1,000, easily exhausted before the project is even evaluated.

**Fix**: WF-08 was deactivated (kept, not deleted, in case a live demo wants guaranteed per-minute sweeping temporarily), and the exact same expiry-sweep logic (call `expire_stale_joint_invitations()`, notify each inviter) was re-wired as a parallel branch off WF-00's **Gmail Trigger** node instead. Because that trigger only executes on real incoming mail, the sweep now costs **zero executions while idle** and only runs exactly when the mailbox has real activity — which is precisely when a grader or user would be testing the system anyway. The 5-minute invitation window itself was never affected by any of this: it's enforced in the database (`joint_account_invitations.expires_at`, checked inside `respond_to_joint_invitation` on every response attempt) independent of whether any sweep ever runs. The only behavioral change is *when the inviter's proactive "it expired" email arrives* — within the same minute as the next piece of mailbox activity, rather than guaranteed within 60 seconds of the actual expiry.

**Resolved (2026-09-15)**: the user recreated `banking-policy-index` at 3072 dimensions (cosine, delete protection on). WF-09 was re-run and seeded all 11 documents in ~4 seconds. **Verified live**: a fresh query ("Do you charge ATM withdrawal fees?") returned `grounded: true, confidence: 0.9, citations: ["doc_atm_fees"]` with the correct Rs 25 / Rs 50 fee breakdown, retrieved in a single search (no retry loop). RAG support is now genuinely grounded end-to-end, not just gracefully falling back.

### Session 5: WF-00 was silently dropping almost every email, and WF-02 had never once succeeded

The user sent a test email (Subject: "Account opening", Body: "Transfer 80K rupees to Imran khan") and noticed the execution looked wrong. It was — and the real bug was far worse than a routing mistake.

**Bug 1 — `Check Pending Joint Invitation` was killing the entire main pipeline for every normal email.** Session 3's fix addressed *false positives* in invitation-response detection, but missed something more basic underneath it: n8n does not run a node's downstream nodes at all when that node outputs zero items. `Check Pending Joint Invitation` returns zero rows for anyone who doesn't have a pending joint invitation — i.e. almost every email, including this test one. Two separate live executions (a real Gmail-trigger poll, execution #187, and a manual re-run, #191) both proved it: `lastNodeExecuted` was `Check Pending Joint Invitation` and nothing else in the workflow ever ran — not intent detection, not profile lookup, not routing, nothing. Every transfer, balance check, policy question, and account-opening request has been silently swallowed since this node was added, unless the sender happened to have a pending joint invitation. The Session 3 false-positive fix was correct but almost moot, since the code it patched (`Detect Invitation Response Intent`) essentially never executed in the first place.

The fix pattern already existed one node away — `Lookup Profile by Email` already had `alwaysOutputData: true` set (from an earlier pass) for exactly this reason, which is why the new-sender / existing-customer branch always worked correctly. `Check Pending Joint Invitation`, added later for the joint-invitation feature, was simply never given the same setting. Fixed by adding `alwaysOutputData: true` to it, so a zero-row result now passes the original email metadata through instead of halting execution — `Detect Invitation Response Intent` correctly reads that as "no pending invitation" (its `rows.filter(r => r.json && r.json.id)` check finds no `id` field on the pass-through item) and the email continues into normal intent classification exactly as before Session 3 ever touched it.

**Bug 2 — WF-02 (Standing Orders) has failed on literally every run since it went live.** `Fetch Due Standing Orders` builds its Supabase filter as a raw query string containing `{{ $now.toISO() }}`, e.g. `...lte.2026-09-15T08:00:27.100+05:00`. n8n does not percent-encode that string before sending it as a URL query string, so the literal `+` in the timezone offset is read as a space by the time it reaches PostgREST — Postgres then rejects `"...100 05:00"` as an invalid timestamp (`22007`). Confirmed against 17 consecutive hourly executions, all failed, going back to the workflow's activation — **not one standing order has ever been processed**. Fixed by switching to `{{ $now.toUTC().toISO() }}`, which ends in `Z` with no `+` character, sidestepping the encoding bug entirely (equivalent value, since `next_execution_at` is `timestamptz`).

**Testing**: WF-02's fix was verified with a fresh live re-run (execution #193) — success, no error (zero orders happened to be due at that moment, which is itself a correct, harmless outcome). WF-00's fix could not be re-verified with a fresh live Gmail-triggered email, because Gmail-trigger workflows cannot be invoked through the available tooling (only re-run via an actual new/unread inbox message, or the n8n editor's own "test workflow" button) — running a full simulated walk of all 61 nodes was deliberately avoided because it risks reaching `Execute WF-01 Transfer Sub-Workflow` for real. Confidence in the fix instead rests on: two real executions reproducing the exact failure, direct inspection of the corrected node config, and the same `alwaysOutputData` mechanism already proven live on the structurally identical `Lookup Profile by Email` node in this same workflow. **Recommended**: send one more test email to see it fully confirmed end-to-end in the execution log.

### Session 7: there was no source of money in the system at all

The user asked the right question: every account opens at Rs 0.00, and the only way money ever moved was customer-account-to-customer-account. If someone emailed "send my brother Rs 7,000," there was genuinely nothing to draw from. This had been true since the very first migration and was never caught until now.

**The fix, not a shortcut.** The obvious quick fix — just `UPDATE accounts SET balance = balance + X` — would have broken the double-entry invariant this schema enforces everywhere else (`run_reconciliation` checks system-wide debits=credits every night). Instead: a real internal account, `TREASURY-MAIN`, funded with Rs 500,000,000 of the bank's own capital, acting as the counterparty for every deposit and loan disbursement via the exact same `process_money_movement()` primitive `execute_transfer()` already uses. It's never customer-owned (no `account_holders` row references it) and never reachable through any email-authenticated intent — only through the new RPCs below.

**Two new ways money enters an account** (migration `006_treasury_deposits_and_loans.sql`):
- **`deposit_funds`**: self-service, capped at Rs 50,000/request and 3/account/24h. A deposit claimed by email is inherently unverifiable — there's nothing more a human reviewer could confirm about a large claim than a small one — so it's bounded rather than escalated to human review, unlike a loan.
- **`apply_for_loan`** / **`approve_loan`** / **`reject_loan`**: flat 10% simple interest, customer-chosen term (1–60 months). Loans ≤ Rs 200,000 auto-approve and disburse instantly, mirroring the same "confident and bounded → no human needed" philosophy as the RAG auto-answer fix in Session 5. Loans up to a Rs 2,000,000 ceiling require a specialist's approval via a new `/webhook/approve-loan` in WF-05 (a second, independent webhook trigger — the existing `/webhook/approve-draft` path for RAG drafts is untouched). Approved loans are repaid automatically via a normal `standing_orders` row (reusing WF-02's existing execution/retry machinery), and `execute_standing_order()` was extended to decrement the loan's `outstanding_balance` and retire it (`paid_off`, standing order `cancelled`) once fully repaid.
- WF-00 gained two new intents, `LOAN_APPLICATION` and `DEPOSIT`, classified from the email body with the same body-first pattern as everything else, with amount/term extraction mirroring the existing transfer-parsing code.

**A bug in the fix itself, caught before it shipped.** The first version of migration 006 funded `TREASURY-MAIN` with a raw `INSERT ... balance = 50000000000` — exactly the "magic balance mutation" the migration's own comment said it was avoiding. `run_reconciliation()` caught it immediately: a 50,000,000,000 discrepancy, because the cached balance had no `ledger_entries` behind it. Fixed in migration `007`: a genesis transaction crediting treasury from a new `BANK-CAPITAL` account (`status = 'closed'` from creation, since reconciliation's per-account check only examines `active`/`frozen` accounts — the correct, schema-consistent place for the one-time offsetting debit a real balance sheet would also carry as paid-in capital). Reconciliation was re-run and passed clean afterward.

**Two more bugs caught by testing before claiming this worked.** The Session 5 auto-answer fix (WF-04 sending grounded RAG answers directly) had never actually been exercised end-to-end — only checked via static wiring. A live test call here surfaced that it had been silently broken the entire time: `support_case_drafts.human_review_state` has a CHECK constraint of `pending/approved/edited/rejected`, but Session 5's fix wrote `'auto_approved'`, which isn't one of them — every single auto-answer attempt had been erroring out at the save step. Fixed to write `'approved'` instead (a value that already existed and is semantically correct — it was approved, just automatically). The very next test call surfaced a second, identical-shaped bug one step later: `support_cases.status` doesn't have an `'answered'` value either (only `open/in_progress/awaiting_human_review/resolved/closed`) — fixed to use `'resolved'`, the same value WF-05 already writes for a human-approved case. Re-tested after both fixes: a real Gmail send confirmed (`labelIds: ["SENT"]`), status correctly `resolved`. This means the Session 5 "fix" had not actually been delivering direct answers until this session — every grounded RAG question was silently falling through to an n8n execution error, which is worse than the original all-human-review behavior it was meant to replace. Lesson applied here and worth carrying forward: **check a CHECK constraint's actual allowed values before writing a new status string into a column that has one** — validated live for every new write path in this session (loans, deposits) rather than assumed.

**A third gap, caught while explaining the feature to the user rather than by an error message.** Nothing stopped a profile from applying for multiple Rs 200,000 loans back to back — each individually under the auto-approve ceiling, so each disbursed instantly with no human ever seeing it, even though the *combined* exposure could exceed what a human would have approved for one large request. Fixed in migration `008`: `apply_for_loan` now rejects a new application while the same profile already has one `pending_review` or `active`. Verified live both ways — a second attempt from a profile with an active loan is correctly rejected; a different profile with no open loan succeeds normally.

### Session 9: a real ops mailbox, email-driven approvals, account-opening details, minors, and the joint-account mandate

Four requests in one pass. The through-line is that a lot of the *schema* for these features already existed from Sessions 2 and 7 — what was missing was any way for a real person, sending a real email, to reach it.

**1. The bank inbox and the ops inbox are now two different mailboxes.** Everything customer-facing still comes from and goes to the bank address. Every request that needs a human decision now goes to a separate ops mailbox, and — this is the new part — the operator decides it **by replying to that email**, not by hand-crafting a `POST` to a webhook.

The mechanism is a generic queue plus a short reference code. `ops_approvals` (migration 009) holds one row per pending decision with a `ref_code` like `OPS-DBD0C32A`; `create_ops_approval()` mints it, `resolve_ops_approval()` applies the decision and dispatches to the real RPC (`approve_loan` / `reject_loan`, releasing a support draft, `release_account_hold`). Three things raise one today: a loan over the Rs 200,000 ceiling (from inside `apply_for_loan` itself, so the alert email has every number it needs without cross-node plumbing), a policy answer the RAG agent couldn't ground confidently (WF-04), and a fraud freeze (WF-03).

On the inbound side, WF-00 gained a `Detect Reference Reply` branch that runs *before* the normal customer pipeline. It pulls an `OPS-` / `JNT-` / `MIN-` code out of the subject or body and reads the decision from what the person actually typed — everything above the first Gmail quote marker — so the APPROVE/REJECT words in the quoted original can't be mistaken for their answer. An `OPS-` code is only actionable when the Gmail sender **is** the ops mailbox; anyone else quoting the code back at us is treated as an ordinary customer email. `JNT-` and `MIN-` codes are authorised in SQL instead (must be a holder of that account; must be the named guardian).

Two deliberate refusals to guess:

- A reply containing **both** APPROVE and REJECT, or neither, is not passed through as `p_accept = false`. An earlier draft did exactly that, which meant a co-holder replying *"no problem, thanks"* would have silently killed a pending transfer, because the word "no" matched the reject pattern. Now it routes to a clarification email and the request stays untouched and pending.
- If the fresh fraud check fails on the final signature of a both-signature transfer, the co-holder's consent is **not** recorded as a rejection (which would close the request and tell them they had declined it). Nothing is recorded, the request stays pending, and both the holder and ops are told the fraud screen stopped it.

**2. Account opening actually asks who you are.** `open_account_with_details()` (migration 015) stores the date of birth and optional phone number on the profile and refuses to open an account when the applicant is under 18. WF-00 parses the date out of the email in four formats (`2010-05-14`, `14/05/2010`, `14 May 2010`, `May 14, 2010`), defaulting the ambiguous numeric form to day-first, and rejects roll-over dates like `2010-02-31` rather than letting `Date` silently slide them into March. No date of birth → we ask for one instead of opening an account. Under 18 with no guardian address → we explain why and ask for one.

**Minors and guardians.** An under-18 applicant creates a `minor_account_requests` row with a `MIN-XXXXXXXX` code; the named guardian gets an email explaining exactly what approving means (only they can move money out; the child can see the balance and receive money; it converts on their 18th birthday) and replies APPROVE or REJECT. On approval, WF-00 creates auth users for whichever of the two aren't customers yet, resolves both profile ids from a single `profiles` lookup — deliberately, so the "already registered" case and the "just created" case take the same path — and `finalize_minor_account_request()` opens the account with the minor as `primary`/`minor` and the guardian as `joint`/`guardian`.

This also switched on a feature that had been inert since Session 2: `promote_minors_to_adult()` was already running nightly in WF-06, but no profile had a `date_of_birth`, so it could never promote anyone.

**3. Joint accounts got their mandate back.** `accounts.authority_model` had existed since migration 004 with two legal values, but nothing ever set it and nothing ever read it, so every joint account was `either_or` by accident rather than by choice. Now the invitation carries it (`create_joint_account_invitation(..., p_authority_model)`), WF-00 parses the customer's own words for it ("both of us must approve" vs "either of us can act alone"), and the invitation and confirmation emails state in plain language which one was chosen and how to change it.

**4. The transfer path had a real hole, and it was not where the mandate was.** `is_holder_transfer_authorized()` — the function that blocks a minor from moving money — was **dead code called by nothing**. `execute_transfer()` performs no holder check at all. The only thing stopping a minor from draining their own account was a check in an n8n Code node, which is not where a banking invariant belongs. `initiate_transfer()` (migration 012) is now the single enforced entry point and checks, in order: the initiator exists, the amount is positive, source is not the destination, both accounts exist, the destination is active, the currencies match, the initiator is a holder, the initiator is not a minor, and only then either executes or parks for signatures. WF-01 already called `initiate_transfer`, so this closed the hole everywhere at once.

**Two bugs found by running it, not by reading it.** `finalize_joint_action_if_complete()` marked an action `approved` *before* executing it and never rolled that back on failure — a both-signature transfer that failed on insufficient funds was left looking approved with no money moved and no retry path. And a fraud assessment has a 10-minute TTL while co-holder consent has a 7-day window, so the assessment captured when the transfer was requested is **always** stale by the time the last signature lands; the first live test failed with `Fraud assessment <NULL> does not exist`. Both fixed in migration 014: the action only becomes `approved` if the thing it authorises actually succeeded, and the consent call accepts a freshly minted assessment that WF-00 obtains from the Python service at the moment of the final signature.

**Verified live, by direct RPC against the real database:** ops approval created, then approved as "ops", disbursing the loan and its repayment standing order, with the double-decide, unknown-reference and unparseable-decision guards all returning the right refusal; both-signature transfer parked, non-holder refused, co-holder signed with a fresh assessment, transfer executed; the same flow again with an over-balance amount, confirming it fails cleanly and stays pending with `last_error` set; account opening refused for a 14-year-old and accepted for a 31-year-old; guardian consent refused for the wrong responder and for a premature finalize, then accepted, then the account opened with the correct holder types; a minor blocked from transferring out of their own account, a non-holder blocked, and the guardian transferring successfully. `run_reconciliation()` passed clean (`total_debits == total_credits`, zero discrepancies) after every one of these.

**Not independently tested:** anything reachable only through WF-00's Gmail trigger, which cannot be invoked through the available tooling. The reply-parsing logic was exercised against nine realistic Gmail reply shapes (approve with a quoted original, reject with a `NOTE:` line, an ambiguous "approve or reject", an impostor quoting an `OPS-` code from the wrong address, guardian approve, co-holder reject with an Outlook-style quote block, two ordinary customer emails, and a subject-line-only reply) in an offline harness, and the full 134-node graph was re-audited for orphans, dangling targets, unwired switch outputs and `$('Node')` references to nodes that don't exist. But no real inbound email has traversed the new branches.

### Session 10: the RAG answer that was never broken, plus closure, automated senders, and a silent dead end

Four problems reported from real inbound email. Three were bugs; one was a misdiagnosis worth writing down, because the wrong fix would have been expensive.

**1. "The RAG throws everything at human support — where are the policy documents even coming from?"**

The reported symptom was that a perfectly ordinary question — *"what's the account opening policy, and how is the loan policy"* — came back as "a specialist will review this", and the ops alert showed `Confidence: 0`. The natural reading is that retrieval found nothing, i.e. that the knowledge base is empty or missing.

That reading was wrong, and it is worth being precise about why. Pulling execution 248 apart showed the agent called the Pinecone tool **twice, and both calls returned exactly the right documents** — the account-opening policy and the loan policy, verbatim, near the top of the results. Retrieval was flawless. What actually failed was the step *after* retrieval: the agent's attempt to return its answer as structured JSON, which errored with `Your request is invalid or could not be processed by the service`.

This is the same failure mode already hit and fixed once in Session 8, where `openai/gpt-oss-safeguard-20b` — the only Groq model available on this account — silently returned an empty tool call when paired with a structured-output parser, and the fix was to switch that path to plain-text output. That fix was applied to the intent classifier and **never applied to the RAG drafting agent**, which still used `outputParserStructured`. So every policy question was reaching a correct, grounded answer and then throwing it away at the last step, and the safety-first fallback did exactly what it was designed to do — refuse to guess, route to a human — for entirely the wrong reason.

Fixed by giving the agent a plain-text contract (`DRAFT:` / `GROUNDED:` / `CONFIDENCE:` / `CITATIONS:` / `NEEDS_HUMAN:` on labeled lines) and parsing it in a Code node into the same `{ output: {...} }` envelope the rest of the workflow already consumed, so nothing downstream changed. The agent node also got `retryOnFail` with two attempts, for transient failures that aren't about output format.

Had the symptom been taken at face value, the "fix" would have been to rebuild the knowledge base — hours of work on the one part of the system that was already working perfectly.

**A bug in the fix, caught by testing it.** The first version of the parser used the `m` regex flag. With `m`, `$` matches end-of-*line*, so the lazy capture for `DRAFT:` stopped at the first blank line. The live test came back grounded and confident with a clean answer — about account opening only. The customer had asked two questions and the loan half had been silently truncated. Anchoring line starts explicitly with `(?:^|\n)` and dropping the `m` flag fixed it; the re-test returned both paragraphs in full. A parser that returns *something* plausible is the worst kind to eyeball rather than test.

**2. The bank was auto-replying to `no-reply@accounts.google.com`.**

A Google security notification landed in the bank inbox, was treated as a customer email, failed the profile lookup, and got the "your email address is not registered with any active customer account" reply — sent to a no-reply address at Google. Harmless here, but the general shape is not: an automated system replying to another automated system is how mail loops start, and it means real bank mail is being generated in response to machine noise.

A guard now runs immediately after metadata extraction and before anything else, matching known automated senders on both the local part (`no-reply`, `mailer-daemon`, `postmaster`, `bounce`, `notifications`, `alerts`, …) and the domain (`accounts.google.com`, bulk-mail providers). A match ends the execution silently: no reply, no support case, no profile lookup. It sits ahead of the reference-code branch deliberately — an automated sender should not be able to reach *any* logic, not merely the customer-facing part.

**3. An ops REJECT on a policy answer left the customer in total silence.**

`Route Ops Decision Outcome` had explicit branches for loan-approved, loan-rejected and policy-approved, and everything else fell through to "no customer email needed". That caught `support_draft` + `reject`. So the sequence was: the customer is told *"you'll receive a follow-up email shortly with the verified answer"*, ops declines the draft, and then — nothing, ever.

The original design note said REJECT "closes the case without emailing the customer", and in isolation that is defensible for spam. But it is indefensible directly after an explicit promise of a follow-up. Added a fourth branch and a graceful decline that tells the customer we can't give a confirmed answer by email, carries the ops note if one was written, and invites them to reply with more detail. Silence is not a decision the customer can act on.

**4. "Delete my account" was not an intent at all.**

There was no `ACCOUNT_CLOSURE` intent, so the request fell through the classifier to `UNKNOWN` and got the generic "our banking assistant could not automatically process your request" reply — for one of the most basic things a customer can ask a bank.

Rather than duplicate closure keywords into both the regex classifier and the LLM path (two ~4KB Code nodes that must be kept byte-identical, a maintenance trap), the rule lives in one new node placed after both paths converge. It **only ever promotes `UNKNOWN`**, which matters: *"what is your account closure policy"* classifies as `POLICY_RAG` and must stay there, and *"close my account and send the balance to ACC-123"* classifies as `TRANSFER` and must stay there — overriding either would actively harm the customer. A confident classification is never second-guessed.

The closure flow itself reuses machinery already built in Session 9 rather than adding a parallel one. `finalize_joint_action_if_complete()` already executed `close_account` for `action_type = 'close_account'`, and `respond_to_joint_action_by_ref()` already handled a holder replying to a `JNT-` code — so the entire confirm-and-execute half existed and needed no new code.

What it did need was a real confirmation step. `request_joint_closure()` inserted the requester's own consent automatically, which on a single-holder account meant `required = 1, consents = 1` and the account closed **instantly** on one unverified sentence in an email. Removing that auto-consent makes every holder — the requester included — confirm via the emailed code, which gives single-holder customers an "are you sure" gate for free and unifies single and joint closure under one mechanism.

`request_account_closure()` runs the blocking checks up front and returns plain language: non-zero balance (with the amount and instructions to transfer it out), active holds, active standing orders, an outstanding or pending loan, already closed, frozen. Doing this before creating the request matters — otherwise the customer gets a confirmation email for a closure that can never succeed, confirms it, and hits an error. Added the loan check that did not exist in `close_account()`: an outstanding loan is a debt to the bank and the account it is repaid from cannot simply disappear.

The handler also refuses to guess which account to close when the customer holds several, and refuses a closure request from a minor holder on a guardian-supervised account.

**A near-miss worth recording.** Adding the eleventh rule to `Route by Intent` shifts the fallback from output index 10 to index 11. The connections were rewired first, in a separate operation from adding the rule — and between those two calls, output 10 was still the fallback, meaning *every unclassified email in the bank* was briefly routed into the account-closure flow. This is the third time in this project that adding a switch rule has silently repointed a fallback (Sessions 7 and 9 both hit it). The audit script that checks rule count against connection count is what catches it; it should be run after every switch change, not just at the end of a session.

**5. Policy documents now exist as documents.**

The complaint that the policy documents "should be somewhere but I couldn't find them anywhere" was fair even though retrieval worked. They existed only as string literals inside an n8n Code node and as a flat list in `docs/policies.md` — nothing a person could sensibly read, review or edit as bank policy.

They are now six real documents in [`docs/policy-documents/`](policy-documents/), rewritten and consolidated from the nineteen snippets: accounts and eligibility, payments and transfers, joint accounts, borrowing and deposits, security/fraud/disputes, and privacy/terms/service standards. They read as policy rather than as retrieval chunks.

WF-09 gained a second, independent branch that reads these from a **Google Drive folder** instead of from code, so policy can be edited by someone who has never opened n8n. It seeds a **separate Pinecone namespace** (`banking_policy_v2`) rather than the live one. That is the important design decision: the six documents are a rewrite of the same subject matter, so seeding them alongside the originals would leave the assistant able to retrieve an old chunk that contradicts a new one — in a banking context, a fee or limit that disagrees with itself. Seeding a parallel namespace means the live bank keeps answering from `banking_policy` until `v2` is verified, the switch-over is one field in WF-04, and rolling back is the same one field.

The Drive branch is **built but not yet exercised**: it needs the six files in a Drive folder and that folder's ID in the `Drive Folder Config` node. Deleting and re-seeding the live namespace was deliberately not automated — a destructive operation against the one component that was verified working is not something to add untested.

**Verified live:** the RAG fix twice via direct sub-workflow execution (grounded, confidence 1.0, answer sent directly with no human step, both questions answered in full after the truncation fix); account closure end to end by RPC — blocked on non-zero balance with the amount quoted, refused for a non-holder, created for a valid request, refused for a non-holder replying to the code, then confirmed and the account actually closed; `run_reconciliation()` clean after all of it. The 146-node WF-00 graph re-audited for orphans, dangling targets, unwired switch outputs, switch-rule/connection alignment and bad `$('Node')` references.

**Not verified:** the automated-sender guard, the closure email chain and the ops-reject email, all of which are only reachable through the Gmail trigger; and the Drive sync, which needs the folder. The Drive branch in particular should be treated as untested until it has run once.

### Session 11: closing the last twelve gaps against the capstone brief

The brief was re-read line by line and every one of its 32 items audited against what actually existed. Twelve had a real gap. All twelve are now built and the table above reads ✅ throughout — but three of those rows deserve more than a status change, because the original reasoning was wrong rather than merely incomplete.

**Where the earlier reasoning was actually wrong**

*#14, reversal into debt.* The original argument was that allowing a negative balance would weaken the ledger's core guarantee, so the feature was declined. The premise was right and the conclusion did not follow. A shortfall does not have to be a negative balance — real banks book it as a **receivable**, which is a different object with different rules. `reverse_transaction()` claws back whatever the recipient still holds through the same double-entry primitive as any transfer, and records the unrecoverable remainder in `account_debts`. `CHECK (balance >= 0)` is untouched, no balance ever goes negative, and the debt is explicit, auditable and separately collectable. Declining the feature to protect an invariant that was never actually threatened cost the project a whole brief item.

*#23, joint dispute rule.* The original argument was that disputes go to a human anyway, so an automation-level rule would be "deciding something a human is about to decide". That conflated *who decides the outcome* with *who gets a say*. A human still decides every dispute. What was missing was the rule governing whose voice is collected first, and that is a real decision with real consequences: raising is deliberately **unilateral**, because requiring a co-holder's permission to report suspected fraud gates the fastest way to stop money leaving behind someone who may be asleep, unreachable, or the problem. Input is then collected from every other holder, and the operator decides with all positions in front of them.

*#15, weekend and holiday scheduling.* The original argument — instant internal settlement means there is no interbank window to miss — still holds, and is why `allow_weekend` remains a legitimate configurable choice. But the column already had three legal values and only weekends were ever honoured. There was no holiday calendar at all, so a payment due on Independence Day simply processed on the day. The reasoning justified a *default*, not the absence of the feature.

**What was built**

*Joint governance (#4, #5, #8).* `remove_holder` and `set_authority` joined `close_account`, `transfer_approval` and `add_holder` as joint action types, so all five inherit the JNT reference code, the email round-trip, the 7-day expiry and the execute-then-approve correctness fix from migration 014. Removal requires every holder to sign **including the person being removed**, and is refused while the account carries a loan or a hold. The mandate and the closure rule are now changeable after opening, with majority closure refused below three holders because on two it is arithmetically identical to unanimous and would only mislead.

*Reversals and debt (#14).* Covered above. The nightly sweep collects outstanding debt from whatever an account receives later, without the balance ever going below zero.

*Business-day calendar (#15) and customer notification (#17).* Pakistan's national holidays are seeded, with the lunar Eid dates flagged `is_estimated` so they are corrected each year rather than silently trusted. And on a permanently failed standing order the **customer** is now told, not only ops — a recurring payment that dies forever without the payer finding out is the kind of failure that is discovered by a bounced rent cheque.

*Interest and statements (#19, #31).* Interest accrues monthly from the treasury through the normal double-entry path, idempotent on `(account_id, period_start)` so the nightly job cannot pay twice. Statements derive their opening balance from the ledger rather than any cached figure, so they are reconstructable from the ledger alone. The Python service gained `/accrue-interest`, `/project-interest`, `/generate-statement` and `/reconcile`, giving it the three responsibilities the brief names instead of only fraud scoring.

*Disputes (#23)* and *RAG safeguards (#25)* and *fraud-pattern search (#29)* as described in the table above.

**Three bugs found by testing, not by reading**

1. **Statement totals were always zero.** `ledger_entries.entry_type` is stored lowercase; the aggregation compared against uppercase. The statement listed every entry correctly and reported `total_credits: 0, total_debits: 0` — output that looks populated and is quietly wrong. Fixed in migration 024, and the Python renderer now refuses to certify a statement where `opening + credits − debits ≠ closing`, so an arithmetic failure can never be emailed to a customer again.

2. **Nobody had agreed to inherit the debt.** Testing add-holder against an account carrying a Rs 315,000 loan raised the obvious question: who consented? The existing holders, and only them. The person being added could not consent even in principle, because `record_joint_consent()` verifies the consenter is already a holder. Joint liability is not something other people can sign you up for, so `accept_holder_addition()` now tracks the invitee's acceptance on the action payload and `finalize` refuses to execute without it.

3. **An invited holder could not answer their own invitation.** `get_joint_action_by_ref()` refused any non-holder, which is correct for every action type except the one where the person who most needs to reply is by definition not a holder yet. Their APPROVE would have come back "you are not a holder of the account this request belongs to". Fixed in 026.

**A pre-existing production problem surfaced by testing.** Exercising the fraud path showed the Python service returning `Supabase credentials missing from environment configuration` — the Railway environment variables flagged in "Known live issues" are still unset. The fail-safe behaved exactly as designed (risk score 100, account frozen, nothing approved), which is the right failure, but **fraud scoring is not actually running in production**; every assessment is currently the safety lock. This is a deployment gap, not a code gap, and it needs the Railway dashboard.

**Verified live, by direct RPC and workflow execution:** business-day adjustment across all three rules including a Friday national holiday; interest accrual and its idempotency on a second run; statement arithmetic before and after the case fix; add-holder with encumbrance disclosure, both-holder approval, invitee acceptance and a wrong-person rejection; authority change to all-signatures plus majority on a 3-holder account; holder removal blocked by an outstanding loan, then completed on a clean account only after the removed party agreed; reversal with partial recovery into debt, then debt settled across two deposits; dispute raised on a joint account with co-holder agreement and disagreement recorded, an outsider refused, and ops upholding it through to a reversal; fraud-pattern retrieval returning the three most relevant typologies; RAG answering two questions in one email, grounded and cited, with no human step. `run_reconciliation()` passed clean after every single one, `total_debits = total_credits` throughout, and zero accounts ever held a negative balance. 15 Python unit tests pass. All 167 WF-00 nodes audited for orphans, dangling targets, unwired outputs, bad `$('Node')` references and — newly — switch rule/connection alignment.

**Not verified:** anything reachable only through the Gmail trigger, which cannot be invoked with the available tooling. That now covers a substantial surface: the statement, dispute, closure, holder-management and automated-sender branches have all been exercised at the RPC layer and audited statically, but no real inbound email has traversed them. The Google Drive policy sync also remains unrun pending a folder ID.

### Session 12: the transfer path was broken for every customer, and the ops mailbox was a customer

This session started from three reports from real use: a transfer refused for no stated reason, a follow-up asking *why* that was answered with a second refusal, and the bank lending money to its own operations mailbox. All three were real, and the first was the worst defect this project has had.

**Every single transfer through the email front door was failing.**

`Execute WF-01 Transfer Sub-Workflow` had no input mapping, so it forwarded whatever items reached it — and what reached it was the **fraud service's HTTP response**: `{approved, risk_score, reason, fraud_assessment_id}`. WF-01 validated that payload, found no `source_account_id`, no `destination_account_id`, no `initiated_by_profile_id` and no `idempotency_key`, and returned its generic failure. The customer was told *"Transfer rejected by banking rules"* — both true and completely misleading: no banking rule was involved, and the transfer was never attempted.

This is the `$json`-after-a-node hazard in its most damaging form yet. A sub-workflow sees the items handed to it, not the parent's history, so the upstream transfer context was simply gone. `Build Transfer Payload` now reconstructs every field explicitly from `$('Resolve Transfer Target & Authorize')` and `$('Look Up Destination Account')`.

**Why it hid.** Every layer underneath was fine and had been tested at the RPC layer — `initiate_transfer()`, the fraud engine, the ledger, idempotency. The broken part was three inches of plumbing between two nodes, and the failure surfaced as a polite, plausible, correctly formatted rejection email. There was nothing in the database to notice, because nothing ever reached the database. This is what the standing "not verified: anything reachable only through the Gmail trigger" caveat was actually costing: not a theoretical gap, a total outage of the bank's main feature.

**"Why was this rejected?" was executed as a new instruction.**

The follow-up contained the word *transfer*, so it was classified `TRANSFER`, found no account number, and replied that the destination could not be identified. The customer asking why their payment failed was told, as the answer, that their payment had failed. `isQuestionAboutPastAction()` now routes an interrogative about a past outcome to support, and a `TRANSFER` carrying neither an amount nor a recipient is reclassified rather than answered with a complaint about what is missing.

**The operations mailbox had a customer profile, an account, and a loan.**

Because every address was a customer address, the ops mailbox had been through account opening like anyone else. When it emailed the bank saying *"Account ACC-… has a loan still outstanding. Tell him his loan is rejected"*, the bank did exactly what it was built to do: ignored the account number in the body (correctly — body-stated identity is never trusted), classified the message as a loan application from the sender, and approved a **Rs 3.00 loan to itself** with a monthly repayment of Rs 0.28.

Every individual rule behaved as designed. The missing concept was that some email addresses belong to the bank.

- `bank_staff` records who works here. Staff addresses are seeded live and deliberately **not** committed, since they are real addresses and this repo is public.
- A trigger on `profiles` refuses to create a customer profile for a staff address. n8n stops it long before the database sees it, but routing is the layer most likely to be edited by mistake, so there is a floor under it.
- `Is Ops Team Sender?` diverts staff mail out of the customer path entirely, ahead of profile lookup.
- The bogus loan was unwound: standing order cancelled, Rs 3.00 returned to the treasury by double entry, loan marked `withdrawn`, account closed, and the profile's address retired to a non-routable tombstone so referential integrity survives while the address leaves the customer namespace.

**Ops can now act, instead of being misread.** Two narrow commands, because a wider parser here moves real money on a guess:

- `credit 5000 to someone@example.com` — a **grant**, not a loan. No interest, no term, no standing order, nothing to repay. This is what the operator was actually trying to do. The customer's email says so explicitly, because "the bank sent me money" should never leave someone wondering whether they now owe it.
- `reject loan for ACC-1234567890` — decide a pending application by naming the customer rather than quoting a reference code.

Anything else gets a reply listing the supported commands, and nothing changes. The reference-code round trip remains the normal path.

**A customer can take back a loan application.** `withdraw_loan_application()` withdraws an application still awaiting a decision and cancels its pending ops approval in the same transaction, so nobody is asked to decide something no longer wanted. It refuses once the money has been disbursed, and says why: the application is finished, what exists now is a debt, and cancelling paperwork does not cancel an obligation. This also unblocks account closure, and the closure refusal now points at it rather than leaving the customer at a dead end.

**Money can be sent to an email address.** Refusing this was over-cautious. The stated reason — "we have no safe way to resolve a name to an account" — is true of *names*; an email address is not a name, it is precisely what this bank authenticates on. `resolve_destination_account()` accepts either form and reports ambiguity instead of resolving it when the recipient holds more than one account. Guessing which of someone's accounts to pay is not a convenience.

The identity rule is unchanged and worth restating, because the two look similar: an address in the body may name **where money goes**; it may never establish **who is asking**. Naming a recipient claims no authority.

**A quoting bug that could have addressed a payment to the bank itself.** The quote-stripping markers were anchored to line starts (`/^\s*On .+wrote:$/m`). Proton Mail on Android delivers the whole reply as **one line**, so no marker matched and the quoted original counted as text the customer had typed — including the bank's own address inside `On … Tony Stark <…> wrote:`. That text is now scanned for recipients. Markers are unanchored and cut at the earliest match anywhere, and the sender's and bank's own addresses are excluded regardless. The same fix went into `Detect Reference Reply`, where the consequence would have been a pending approval decided by the quoted message rather than by the person replying.

**Two smaller defects found while in there.** `Finalize LLM-Classified Intent` re-derived amounts, terms and recipients with its own copy of the extraction logic, so the keyword path and the model path could disagree about how much money to move; it now only relabels the intent. Its `validLabels` list was also missing `ACCOUNT_CLOSURE` and `STATEMENT` even though the model was instructed to emit them, so an LLM-classified closure or statement request was silently coerced to `UNKNOWN` and answered generically.

**The Google Drive sync is live.** The files were already in the folder; it only ever needed the ID. Two things surfaced on the first run. `README.md` was embedded as bank policy — it explains Pinecone namespaces and folder IDs, exactly the wrong thing for a customer question to retrieve. And the sync *appended*, so re-running after editing a document left the old text retrievable beside the new; that was a documented caveat which made the pipeline useless for corrections, which is what a policy pipeline is for. The staging namespace is now cleared before seeding, so a re-run replaces rather than accumulates, and WF-04 answers from `banking_policy_v2`. The clear targets `banking_policy_v2` only, never the live namespace.

**Railway is fine, and Session 11's report of it is out of date.** The environment variables have since been set; `/assess-fraud` returns real rules-engine scores against live data. The deeper problem was that this was unanswerable without moving money: `/health` returned `{"status": "ok"}` whether or not the service could reach the database, so a misconfigured deployment looked healthy and its only symptom — every transfer blocked — looked like fraud detection working. `/health` now reports whether the credentials are present and whether the database actually answers. It stays HTTP 200 when degraded on purpose: Railway restarts a container that fails its health check, and restarting does not supply a missing environment variable.

**An unauthenticated endpoint that could approve loans.** Five workflows expose public webhooks wired to live logic: `/webhook/transfer`, `/assess-fraud`, `/support-case`, `/approve-draft`, `/approve-loan`. None has any authentication.

Three of them — WF-01, WF-03, WF-04 — are **inert**. Each declares `responseMode: responseNode` with no Respond to Webhook node present, so n8n errors at the trigger before any downstream node runs (verified, execution 302).

**WF-05 is not.** It has eight Respond to Webhook nodes, so both of its endpoints work. `POST /webhook/approve-loan` with an empty body returned `{"success": false, "error": "loan_id must be a valid UUID"}` — it parsed the request and answered. With a real loan id and `action: approve` it would have called `approve_loan`, disbursed the money and emailed the customer, for anyone who knew the URL.

This was initially reported as "all five are inert", which was wrong: WF-04 was checked and the conclusion generalised to the other four without checking them. The distinction that mattered — whether a Respond to Webhook node exists — was visible in the node list the whole time.

**WF-05 is now unpublished**, and both endpoints return 404. Nothing broke: no workflow references it, and everything it did is already done by the `OPS-` reference-code flow in WF-00 — loan approved/rejected emails, the reviewed policy answer, the rejected policy answer, and the draft/case state changes and audit entries that `resolve_ops_approval()` writes in SQL. It was superseded when ops moved to email and simply left running.

Unpublishing rather than deleting because it is reversible and closes the hole immediately. Deleting WF-05 outright, and removing the three inert webhook triggers, is still worth doing.

**Verified live:** the fraud service against real accounts (score 15, "new recipient" — a real rules-engine answer, not the fail-safe); a Rs 100.00 transfer end to end through the same call WF-01 now makes, ledger balanced afterwards; idempotency, by replaying the key and getting the original transaction id back with the balance debited once; `resolve_destination_account()` across an account number, an email address, an ambiguous recipient holding three accounts, an unknown address, an unknown account number and a staff address; `withdraw_loan_application()` on a genuinely stuck application — the Rs 500,000 pending loan that had been blocking account closure — including its cancellation of `OPS-DBD0C32A`, the refusal to withdraw a disbursed loan, and a second call reporting nothing pending; `operator_credit_account()` crediting by email address with no loan and no standing order created, and refusing a non-staff caller; the staff-profile trigger refusing a customer profile for the ops address; the Drive sync clearing and re-seeding six documents with README correctly skipped. `run_reconciliation()` passed after every step. 17 Python tests pass. All 187 WF-00 nodes audited clean.

**Not verified:** the new email-driven branches — ops commands, loan cancellation, transfer to an email address — have been exercised at the RPC layer but not through a real inbound email. Given that this session's headline bug was invisible from the RPC layer, that distinction deserves to be taken seriously rather than treated as a formality.

### Session 12, second pass: blank emails, the recipient, and a real operations team

**Four ops emails were rendering blank fields and `Rs NaN`.** Each sat downstream of another Gmail node, so its bare `$json` was the Gmail *send response* — `{id, threadId, labelIds}` — and every business field resolved to undefined. The email still sent, still looked well formed, and said nothing.

Three were introduced in this session. The fourth, `Alert Ops - Dispute Raised`, had been broken since Session 11 and was never noticed because the dispute path had only ever been exercised by RPC.

`n8n/validate_workflows.py` now fails the build on it: any node whose predecessors are all Gmail nodes and which reads a `$json` field other than `id`/`threadId`/`labelIds` is reported by name. This is the same class of hazard as the switch-fallback one and it is now caught the same way — automatically, rather than by someone noticing an email that reads oddly.

**The recipient is told the money arrived.** Only the sender was ever emailed, which is the half that already knew. `Transfer Completed?` gates on the sub-workflow's `success` rather than on the response email, which is sent for both outcomes; `Split Recipient Holders` emails every holder of the destination account and skips the sender, so moving money between two accounts you hold does not email you twice. The notice names the sender's name and account number but not their email address.

**The operations team is a team now.** `Is Ops Team Sender?` compared the sender against one hardcoded address, so a second operator could never have worked no matter what the database said. `Check Sender Is Staff` asks `staff_check()` on every inbound email; `Detect Reference Reply` takes both the team inbox and the staff verdict from it, and any operator can answer an `OPS-` code rather than only the mailbox it was addressed to.

**Joining the team by pass phrase.** `PASSPHRASE: <phrase>` from an address that holds no accounts enrols it; `NEW PASSPHRASE: <phrase>` from an existing operator rotates it. The security reasoning is in `database.md` under migration 028. The two forms are deliberately distinct words rather than the same syntax meaning different things depending on who sent it.

Adding the third rule to `Route Ops Command` moved its fallback from output 2 to output 3. Rule and rewiring went in one atomic update, as they now always do.

### Session 12, third pass: what only real email could find

Five defects, every one of them invisible to the database tests and to the static audit, and every one found by an actual message arriving.

**A missing subject line read as a rejection.** n8n substitutes the literal string `"No Subject"` when an email has none. That string went into the APPROVE/REJECT detector, where **"No"** matches the rejection pattern — so an email saying only `APPROVE OPS-97EBF6C8` contained an approval *and* a rejection, was correctly judged ambiguous, and left the request pending. Every decision type was affected: loans, disputes, joint consents, guardian consents, staff enrolment. A placeholder is not something the sender typed, so it no longer gets a vote.

This one is worth dwelling on. The "never guess at an unclear answer" rule is right, and it worked exactly as designed — it just happened to be fed a word the customer never wrote.

**A date of birth was read out of a quote header.** `Extract New Sender Intent` parsed the whole message body, quoted text included. Someone replying with only the missing detail — their guardian's address — had their DOB taken from Gmail's `On Wed, Sep 16, 2026 at 1:28 PM ... wrote:` line, producing a date of birth of *today*. Date of birth is the field that decides whether an applicant needs a guardian at all.

Quote-stripping had been added to the intent classifier, to `Detect Reference Reply` and to `Parse Ops Command` — and missed here. The fix reads only what the sender typed, and falls back to the quoted thread solely for a date explicitly **labelled** as a date of birth, never a loose one, because a loose date in quoted text is far more likely to be a timestamp than a birthday.

**A hardening check took every approval down.** Covered in `database.md` under migration 030: `resolve_ops_approval` runs as `banking_functions`, the `is_bank_staff` helper it calls was granted only to `service_role`, and the result was `permission denied` on every ops decision in the bank. The check itself was correct; the owner it would run as was not considered.

**Every operations reply went to the team inbox rather than to the operator who sent the command.** Invisible while the team was one address. The moment there were two, the wrong person was told and the sender heard nothing.

**An operator was refused a credit and the administrator was never told.** A refused attempt to create money out of the treasury is exactly what the person holding that power should see. The administrator now gets it, with the two commands to respond — issue it themselves, or remove the operator.

**And a queue that could become invisible.** If an alert email is lost, filed as spam or deleted, the request sits in the queue until it expires seven days later with nobody having decided it. `list pending approvals` means an operator can ask instead of depending on a message having arrived. Migration 031.

**A near-miss worth recording.** A shell heredoc silently turned the `\b` word boundaries in a new regex into literal backspace characters (`0x08`), which would have made the command never match. Caught before deploying by reading back what was actually written rather than what was intended. All workflow files are now scanned for stray control characters.

**Verified by real email this session:** transfer by account number and by email address, recipient notification, deposit, statement, balance, loan application, loan approval through an `OPS-` code (with no subject line), loan cancellation, administrator credit, operator credit refused, operator enrolment by pass phrase, administrator approval of it, operator removal, a removed operator having no powers, the joining phrase misused by an existing operator, dispute raised and upheld, joint account invitation and acceptance, additional account opening, minor account with guardian consent, unauthorised access refused, and an ops command the bank would not guess at. `run_reconciliation()` clean throughout, debits equal to credits, no account ever negative.

**Still not verified by email:** account opening for a brand-new **adult**. Every address available holds an account or is staff, and Gmail plus-addressing cannot be used as a sending address, so there was no way to present the bank with an unknown adult. The minor path exercises the same node and the same routing, and `open_account_with_details()` is verified by RPC — but the adult branch of `New Sender Route` has not had a real email through it, and should not be described as though it has.
