# Engineering Decisions — Edge Case Checklist

This document works through every item in the capstone feature list PDF (`Digital Banking Backend + Ops Automation — Capstone feature list`, 7 domains, 32 items) and records the actual, justified decision for each: what was built, what was deliberately scoped out, and why. Cross-references point at the real schema (`supabase/migrations/`), RPCs, and n8n workflows (`n8n/workflows/`) rather than restating them.

Status legend: **✅ Built** — implemented and live · **⚠️ Partial** — a simplified version is built · **⛔ Scoped out** — deliberately not built for this submission, with reasoning.

---

## 1. Account Types & Ownership

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 1 | Single-holder account creation and management | ✅ Built | `accounts` + `account_holders` with `role = 'primary'`. This is the baseline path exercised by every test scenario. |
| 2 | Joint account creation with 2+ holders | ✅ Built | Multiple `account_holders` rows per `account_id`, `role = 'joint'`. Seed data includes `TEST-JOINT-001` with Alice + Charlie. |
| 3 | Either-or vs. both-signatures authority model | ⛔ Scoped out | `account_holders` has no authority-model column. **Decision: default to either-or (any holder can act unilaterally) for all joint actions except closure**, which is the one place the PDF explicitly calls for stronger protection (see #4). Both-signature authority for ordinary transfers would need a pending-approval table mirroring `joint_account_actions` for every transaction type, which is real scope for a v2, not a schema flag. |
| 4 | Mutual consent requirement for removing a joint holder | ⛔ Scoped out | Only account *closure* has a consent workflow (`joint_account_actions` / `joint_account_consents`, action_type constrained to `'close_account'`). Removing a single holder while keeping the account open is a different state machine (who inherits their share of holds/standing orders?) and was not built. Decision: unsupported in this MVP; the only supported multi-holder action is full closure. |
| 5 | Majority-vote vs. either-or authority for 3+ holder joint accounts | ⚠️ Partial | `record_joint_consent()` requires **unanimous** consent (checks that every holder has responded and every response is `consent = true`) before `close_account()` fires — not majority-vote, and not either-or. Decision: unanimous consent is the conservative default for the one high-stakes joint action we support (closure). Majority-vote was rejected as a default because it lets 2 of 3 holders close an account and force a payout split the third holder never agreed to — too risky to ship without a dispute-resolution path behind it. |
| 6 | Minor/guardian account with guardian-acts, minor-views-only permissions | ⛔ Scoped out | No age/guardian columns on `profiles` or a permissions layer on `account_holders`. This needs a `role IN ('guardian','minor')` distinction plus a permissions matrix (minor: SELECT only; guardian: full CRUD) enforced in RLS *and* in every n8n intent handler. Real effort, not a flag. Decision: out of scope; `account_holders.role` stays `primary | joint | beneficiary`. |
| 7 | Age-based trigger to convert minor account to full access | ⛔ Scoped out | Depends on #6 existing first (no `date_of_birth` on `profiles` either). Would be a nightly scheduled RPC similar to `run_reconciliation()`. Not built. |
| 8 | Adding a new holder to an account with existing debt/holds | ⛔ Scoped out | There's no "add holder" RPC at all today — holders are only ever seeded or created at account-opening time. `place_account_hold` and negative-balance tracking exist, but nothing stops (or explicitly permits) attaching a new `account_holders` row to an account that already has an active hold. Decision: until an explicit "add holder" flow is built, this can only happen via direct DB access, which is an ops action, not a customer-facing one — so it's not a live edge case yet. |
| 9 | Joint account closure rule when holders disagree | ✅ Built | Unanimous-consent model means disagreement = the request simply never reaches 100% approval. `joint_account_actions.expires_at` (7 days, see migration `001`) auto-times out a stalled request rather than leaving it open forever. No forced closure over a dissenting holder — matches the conservative posture in #5. |

## 2. Transactions & Transfers

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 10 | Idempotency key handling to prevent duplicate transfer submissions | ✅ Built | `idempotency_keys` table, atomic `INSERT ... ON CONFLICT DO NOTHING` inside `execute_transfer()`. A retried key with a `completed` status returns the stored result instead of re-executing. WF-00 derives the key deterministically from the Gmail `messageId` (`gmail_<messageId>`), so re-sending the same email is naturally idempotent. |
| 11 | Postgres transaction isolation to prevent concurrent-withdrawal overdrafts | ✅ Built | `execute_transfer()` takes `SELECT ... FOR UPDATE` row locks on both accounts (in a fixed account-id order to avoid deadlocks) before checking `get_available_balance()`, inside one Postgres transaction. `tests/test_concurrency.sql` exercises this directly. |
| 12 | Rollback logic for partial transfer failure (debit succeeds, credit fails) | ✅ Built | The whole transfer — idempotency check, lock, fraud check, hold check, balance check, both ledger inserts, both balance updates, audit — runs inside the single `execute_transfer()` PL/pgSQL function body. Any exception anywhere rolls back the entire function atomically; there is no code path where a debit can commit without its matching credit. |
| 13 | Notification flow when a transfer is rolled back | ✅ Built | WF-01's `Check RPC Result` branch on `success = false` and emails an ops alert (`Email Ops - Transfer Failed Alert`) with the error and idempotency key; WF-00 separately emails the customer a plain-language failure notice with no funds-moved confirmation. |
| 14 | Reversal/chargeback handling after funds already spent (negative balance/debt tracking) | ⛔ Scoped out | `accounts.balance` has `CHECK (balance >= 0)` — the schema actively **forbids** negative balances. A real chargeback-after-spend flow needs a separate `debt_ledger`/`overdraft` concept that intentionally violates the "balance is truth, never negative" invariant everywhere else in the system. Decision: rather than special-case one table to allow negative balances (weakening the ledger's core guarantee), this is left as a documented gap — a dispute that nets to a loss becomes an ops-managed write-off outside the automated ledger, not an automated negative-balance entry. |

## 3. Standing Orders / Scheduled Payments (n8n)

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 15 | Weekend/holiday scheduling rule (process early, late, or pending state) | ⛔ Scoped out | WF-02 runs hourly and fires any order where `next_execution_at <= NOW()` — no calendar/holiday awareness. Decision: for a hackathon-scope banking backend, real-time ACH-style settlement isn't gated by banking-holiday calendars the way real interbank rails are (this system settles instantly, internally, via the ledger) — so the holiday-deferral problem this rule solves for real banks doesn't apply here. Documented as a known simplification rather than silently ignored. |
| 16 | Insufficient-funds retry policy (same day, next day, max retry count) | ✅ Built | `execute_standing_order()` increments `standing_orders.retry_count` on failure and reschedules; WF-02's `Permanent Failure?` node checks `retry_count >= 3` (max 3 retries) OR an explicit `'failed'` status from the RPC, and disables the order permanently past that point. |
| 17 | Customer notification when a standing order permanently fails | ✅ Built | WF-02 → `Format Permanent Failure Alert` → `Email Ops Team - Standing Order Failed`. Note: this currently emails **ops** (`metonystar1@gmail.com`), not the customer directly — decision: a permanently-failed recurring payment is treated as an ops-triage event first (does the customer need outreach, is this a systemic issue, etc.) rather than an unsupervised customer email, consistent with the "always requires human sign-off" boundary in domain 6. |
| 18 | Race-condition handling when a standing order is edited/deleted mid-execution | ✅ Built | `standing_orders.execution_locked_at` is a stale-lock timestamp column: `execute_standing_order()` locks the row before executing, so a concurrent edit/delete blocks on the same row lock rather than racing the in-flight execution. |

## 4. Interest, Statements & Reconciliation (Python)

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 19 | Nightly reconciliation job comparing ledger sum vs. reported balance | ✅ Built | WF-06 (midnight UTC cron) → `run_reconciliation()` RPC checks (a) system-wide `SUM(debits) = SUM(credits)` and (b) every account's cached `balance` against its ledger-entry sum. Results land in `reconciliation_runs`; a mismatch triggers `Email Ops Team - Reconciliation Mismatch`. Note: the PDF frames this as a Python job, but it's implemented as a Postgres RPC triggered by n8n's scheduler — the actual arithmetic is simple aggregate SQL, and running it inside Postgres means it reads the ledger under the same transactional guarantees that wrote it, with no network round-trip that could see a half-committed state. Interest calculation itself (the other half of this domain's Python framing) was not built — no interest-bearing account type or rate schedule exists yet. |

## 5. Fraud, Disputes & RAG-Based Support

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 20 | RAG-based auto-draft response to customer support queries | ✅ Built | WF-04: LangChain agent (Groq `openai/gpt-oss-safeguard-20b`) with a Pinecone-retrieval tool (`banking-policy-index`, namespace `banking_policy`, Gemini `text-embedding-004` embeddings), structured JSON output (`draft`, `grounded`, `confidence`, `citations`, `needs_human`). **Live status: the Pinecone index does not currently exist** (verified via a live test call — `404` from the Pinecone API), so retrieval always comes back empty. This is an infrastructure gap, not a design gap — the agent, prompt, and fallback path are correct; the index just needs to be created and seeded. See `docs/architecture.md` follow-up / README known-issues. |
| 21 | Hallucination guardrails so RAG never invents non-existent policy | ✅ Built | The agent's system prompt hard-bans inventing policy and requires citations; `Grounded & Confident? (>= 0.7)` gates on both `grounded = true` AND `confidence >= 0.7`. Below that bar, `Insufficient Policy Fallback Draft` overrides the model's own text entirely with a fixed "requires specialist review" message — the LLM's raw draft is never sent to a customer when it isn't grounded, regardless of how confident-sounding it is. |
| 22 | Immediate fraud-flag hold trigger and false-positive handling for legitimate large purchases | ✅ Built | WF-03: risk score ≥ 75 → `place_account_hold()` full freeze, `fraud_investigation` type, ops alert. False-positive handling is `release_account_hold()` — but this is intentionally **not** an automated appeal path (customer can't self-clear a fraud hold); it requires a human operator to invoke the release RPC. See domain 6 (#26). |
| 23 | Dispute resolution rule for joint accounts (unilateral vs. both-holder input) | ⛔ Scoped out | WF-00's `DISPUTE` intent only sends an acknowledgement email and relies on a human specialist for the actual investigation (see `Send Dispute Acknowledgement Email`); there's no automated joint-account-specific dispute rule. Decision: disputes are inherently investigative and already routed to a human by design (domain 6), so an automation-level unilateral-vs-both-holder rule would be deciding something a human is about to decide anyway — redundant to build. |
| 24 | Human approval gate before any RAG-drafted response is sent via Gmail | ✅ Built | WF-05 is the sole path that can send a `support_case_drafts` answer to a customer: it requires an explicit `POST /webhook/approve-draft` with `action: approve|edit|reject`, checks `human_review_state = 'pending'` before allowing any transition, and only the approve/edit branch reaches the Gmail send node. |
| 25 | Safeguards against Pinecone surfacing a similar-but-wrong past case for drafting | ⚠️ Partial | The confidence/grounded threshold (#21) is the safeguard that exists today — a wrong-but-similar match that the LLM can't stitch into a confident, citation-backed answer gets routed to a human instead of sent. What's **not** built: explicit metadata filtering (e.g. product line, jurisdiction, account type) on the Pinecone query to stop a similar-sounding-but-wrong-category document from being retrieved in the first place. Decision: out of scope until the index itself is populated with real policy documents that have that metadata to filter on. |

## 6. Approval & Autonomy Boundaries

| # | Edge case | Status | Decision & justification |
|---|---|---|---|
| 26 | Explicit list of actions automation may take unsupervised | ✅ Built (documented here) | **Unsupervised:** balance inquiries (read-only, authorization-checked); transfers between accounts the sender demonstrably holds, gated by the deterministic Python fraud score (not an LLM); standing-order execution/retry; nightly reconciliation; RAG *drafting* (never sending); receipt/acknowledgement emails for support, dispute, and account-opening inquiries. |
| 27 | Explicit list of actions always requiring human sign-off | ✅ Built (documented here) | **Always human:** sending any RAG-drafted policy answer to a customer (WF-05 gate); releasing a fraud hold (`release_account_hold` takes a `released_by_profile_id` and is never called automatically by any workflow); joint account closure is gated by the account holders themselves via explicit consent, not by n8n; reversing a completed transaction (no automated reversal RPC exists — see #14); removing/adding joint holders (unbuilt, #4/#8, so implicitly human-only via direct DB access today). |

## Known live issues at time of this audit (2026-09-14)

These are infrastructure/config problems found and partially fixed during this review — see `README.md` "Known Dependencies" for current status:

1. **n8n → Railway Python service URL was missing its `https://` scheme** in the `PYTHON_SERVICE_URL` instance variable, causing every fraud check to error and fail safe into a hold. Fixed in WF-00 and WF-03 by normalizing the URL in the HTTP Request node itself instead of trusting the variable's format.
2. **`place_account_hold` RPC response broke n8n's JSON auto-detect** (it `RETURNS UUID`, a bare scalar, unlike every other financial RPC which returns `JSONB`) — fixed by forcing `responseFormat: text` on that HTTP Request node.
3. **The Railway-deployed Python service itself is rejecting requests** with `"Supabase credentials missing from environment configuration"` — its `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` environment variables need to be (re)set directly on Railway. This could not be fixed remotely because it requires entering a secret key into Railway's dashboard, which is a manual, credential-handling step.
4. **The Pinecone index `banking-policy-index` does not exist** (404 from Pinecone's API during a live test). RAG support degrades gracefully to "needs human" rather than crashing, but there is currently no real grounded retrieval happening. Needs the index created and seeded with policy documents.
5. Two of the three published n8n workflow drafts (WF-00, WF-01, WF-04) had newer, safer logic sitting unpublished in the editor — the *live* versions had hardcoded fallback account IDs and a hardcoded fallback "approved" fraud-assessment ID that would activate on malformed input instead of rejecting the request. Republished all three to their improved drafts as part of this review.
